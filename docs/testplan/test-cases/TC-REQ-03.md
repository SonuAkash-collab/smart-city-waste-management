### TC-REQ-03: Track request status and cancel before Scheduled

| Field | Content |
|---|---|
| TC ID | TC-REQ-03 |
| Title | Verify Citizen request status tracking and cancellation rules |
| Requirement(s) | SCW-F-012, SCW-F-013 |
| Type | Functional |
| Objective | Verify that a Citizen can retrieve their collection request and see its current status, that all documented status values are returned, and that cancellation succeeds only before Scheduled. |
| Preconditions | 1. The Request Service is reachable in the test environment using the REST/JSON API under `/api/v1`. 2. An authenticated Citizen request context is available to access that Citizen's own requests. The environment-specific API base URL and the approved method of provisioning the test identity and bearer token require team confirmation. 3. Test requests can be made available in each required status, and a method exists to verify their current stored status and whether a cancellation conflict leaves it unchanged. The source documents do not define the test-data setup or verification mechanism; the team must confirm them. |
| Test data | Use requests belonging to the authenticated Citizen, prepared in the statuses `SUBMITTED`, `APPROVED`, `SCHEDULED`, `COLLECTED`, `REJECTED`, `MISSED`, and `CANCELLED`. Use separate requests in `SUBMITTED` and `APPROVED` for successful cancellation checks. Use separate requests in `SCHEDULED`, `COLLECTED`, and `MISSED` for cancellation-conflict checks. The way to prepare or observe these states requires team confirmation. |
| Steps | 1. For each request prepared in one of the seven documented statuses, call `GET /api/v1/requests/{id}` using the authenticated Citizen context and record the returned status. 2. For a separate request with status `SUBMITTED` and another with status `APPROVED`, call `DELETE /api/v1/requests/{id}` as the owning Citizen. Record each response, then retrieve each request with `GET /api/v1/requests/{id}` and record its status. 3. For separate requests with status `SCHEDULED`, `COLLECTED`, and `MISSED`, call `DELETE /api/v1/requests/{id}` as the owning Citizen. Record each HTTP status, then retrieve each request with `GET /api/v1/requests/{id}` and record its status to check that it is unchanged. |
| Expected result | Step 1: Each `GET /api/v1/requests/{id}` returns HTTP 200 with the full request object, and its status matches the request's current stored status: `SUBMITTED`, `APPROVED`, `SCHEDULED`, `COLLECTED`, `REJECTED`, `MISSED`, or `CANCELLED`. Step 2: Each DELETE for a request before `SCHEDULED` returns HTTP 200 with `{"id":101,"status":"CANCELLED"}` (where `id` is the request ID); subsequent GET returns the request with status `CANCELLED`. Step 3: Each DELETE for a request at `SCHEDULED` or later returns HTTP 409; subsequent GET confirms the request status is unchanged. |
| Pass/fail criteria | Pass if the Citizen's GET response reports the current stored value for every supported status, DELETE returns HTTP 200 and changes the status to `CANCELLED` for requests before `SCHEDULED`, and DELETE returns HTTP 409 without changing status for requests at `SCHEDULED` or later. Fail if any observed result differs. If the required authenticated context, status-specific test requests, or verification method is unavailable, mark the affected checks Blocked rather than assuming credentials, database state, or status setup. |
| Actual result | |
| Status | Not run |

The API contract specifies `GET /api/v1/requests/{id}` for the request owner or Admin, with HTTP 200 returning the full request object. For cancellation it specifies `DELETE /api/v1/requests/{id}` for the owning Citizen, HTTP 200 with `{"id":101,"status":"CANCELLED"}`, and HTTP 409 if the request is `SCHEDULED` or later. The API contract and project sources do not specify how to prepare requests in every status or independently observe stored status; those test setup and verification arrangements require team confirmation.
