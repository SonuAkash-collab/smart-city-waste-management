### TC-REQ-02: Priority assignment and Admin override

| Field | Content |
|---|---|
| TC ID | TC-REQ-02 |
| Title | Verify automatic request priority by waste type and age, and Admin priority override |
| Requirement(s) | SCW-F-011 |
| Type | Functional |
| Objective | Verify priority assignment for the waste types supported by the approved API enum, one-level escalation for requests remaining Submitted or Approved after 48 hours (capped at High), and Admin priority override behavior. |
| Preconditions | 1. The Request Service is reachable in the test environment using the configured REST/JSON API under `/api/v1`. 2. Authenticated Citizen and Admin request contexts are available for their own requests and Admin operations. The environment-specific API base URL and the approved method of provisioning these identities and bearer tokens require team confirmation. 3. A team-confirmed test-data or clock-control method is available to represent requests in Submitted and Approved states after 48 hours; the project documents do not define such a method. |
| Test data | Submit requests using the documented POST fields: `latitude`, `longitude`, `address`, `wasteType`, and `estimatedQuantityKg`. For automatic assignment use the seven allowed waste types: `HAZARDOUS`, `MEDICAL`, `E_WASTE`, `MIXED`, `RECYCLABLE`, `GARDEN`, and `BULKY`. Expected priority groups for these API-supported values: `HAZARDOUS`, `MEDICAL`, `E_WASTE` → `HIGH`; `MIXED`, `RECYCLABLE` → `MEDIUM`; `GARDEN`, `BULKY` → `LOW`. A separate `general` category is not included in the approved API enum; whether it requires distinct test coverage or how it is represented requires team/teacher confirmation. For aging, use requests represented as Submitted and Approved after 48 hours, with starting priorities that exercise Low → Medium, Medium → High, and High → High (cap) in each status. For Admin override, use separate eligible requests and each override value: `HIGH`, `MEDIUM`, and `LOW`. |
| Steps | 1. Using the authenticated Citizen request context, submit one request for each waste type in the automatic-assignment test data using `POST /api/v1/requests`; record each response's `id` and `priority`. 2. Using the team-confirmed method, prepare requests that remain in each of the Submitted and Approved statuses after 48 hours, covering Low → Medium, Medium → High, and High → High for each status. Retrieve each request using `GET /api/v1/requests/{id}` as its owner or Admin and record its status and priority. 3. For separate requests, use the authenticated Admin context to call `PATCH /api/v1/requests/{id}/status` with `{"status":"APPROVED","priority":"HIGH"}`, then repeat with `MEDIUM` and `LOW` on separate requests. Record each PATCH response. 4. Retrieve each overridden request using `GET /api/v1/requests/{id}` and record its priority. |
| Expected result | Step 1: Each POST returns HTTP 201 with `id`, `status`, `priority`, and `createdAt`; the returned initial priority matches the expected group for that waste type. Step 2: For requests remaining Submitted or Approved after 48 hours, priority rises exactly one level: Low to Medium, Medium to High, and High remains High. Step 3: Each Admin PATCH returns HTTP 200 with `id`, `status`, `priority`, and `updatedAt`; the returned priority equals the requested override. Step 4: GET by ID returns HTTP 200 with the full request object, and its priority equals the saved override. |
| Pass/fail criteria | Pass if all seven API-supported waste-type priority assignments, age-based one-level increases and the High cap, and all three Admin override values are observed through the documented responses. This result does not establish coverage for a separate `general` category. Fail if any tested result differs. If authenticated test contexts or a team-approved way to represent request age/state are unavailable, mark the affected checks Blocked rather than assuming credentials, stored data, timestamps, or database access. |
| Actual result | |
| Status | Not run |

The API contract documents `PATCH /api/v1/requests/{id}/status` with status `APPROVED|REJECTED` and optional priority override; Admin override testing therefore uses the documented `APPROVED` status and separate requests. The API and SRS do not define how request age is set or controlled in a test, so the aging checks require the confirmed test-data or clock-control method noted above.
