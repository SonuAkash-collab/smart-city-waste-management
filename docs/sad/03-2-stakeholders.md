### 3.2 Stakeholders and Concerns

| Stakeholder | Goals and concerns | Responsibilities and system interactions |
|---|---|---|
| Citizen | Submit and track waste collection requests, cancel before a request is Scheduled, and receive status notifications. Personal data and home-location confidentiality are security objectives (SCW-SO-1). | Registers and logs in, submits a request with its location, waste type, estimated quantity and optional photo, tracks status, cancels an eligible request, and receives in-app/email notifications through the Web Frontend. |
| Collection Vehicle Driver | View the assigned route as ordered stops on a map and record whether stops are Collected or Missed. | Uses the Web Frontend to view the assigned route and mark stop outcomes; stop updates are handled by the Route Optimization Engine and update request status. |
| Admin / Municipal Officer | Manage collection operations and access operational status, reports and route generation. Integrity and accountability of request, route and facility data are security objectives (SCW-SO-2). | Uses the Web Frontend to view, filter, approve and reject requests; override request priority; manage vehicles, facilities and user accounts; generate routes; view the dashboard; and export daily collection reports as CSV. Admin actions are written to the audit log (SCW-SEC-006). |
| Disposal Facility Operator | Record incoming waste and manage facility capacity. | Uses the Web Frontend to record incoming waste by vehicle and weight; the Facility Service updates remaining capacity. |
| Municipal officers (client / product owner) | Ensure the requirements and intended waste-collection workflow reflect municipal needs. | Review the requirements and intended waste-collection workflow from a municipal perspective. Working assumption: this review is consultative; this document assigns no formal sign-off authority or approval process. |
| Team 04 developers, architects and testers | Implement the agreed design and verify it against the SRS and Test Plan. | Develop and test the system using the documented components, APIs and requirement traceability. The project context identifies Sonu Akash as lead / integrator and the other members as team members; this section assigns no individual system-operation responsibilities beyond the documented development and testing work. |
| Course instructors / evaluators | Assess the completeness and quality of the project deliverables. | Review the SRS, SAD and Test Plan; this section assigns no responsibilities for operating the deployed system. |
| OpenStreetMap and SMTP email provider | Provide external map and geocoding services and email delivery on which parts of the system depend. | OpenStreetMap supplies map tiles and geocoding; the SMTP email provider sends status-change email notifications. SRS Section 4.6 specifies that in-app notifications are still created if the email provider is unavailable. Working assumption: OpenStreetMap unavailability may degrade map display. Provider responsibilities are limited here to the stated services; no service levels or formal provider agreements are assumed. |

The system uses a layered (3-tier) architecture: the Web Frontend presents role-appropriate functions, FastAPI services implement application behavior, and PostgreSQL stores persistent data. Working assumption: stakeholder responsibilities are limited to those listed above; this section assigns no additional decision rights, municipal approval process, or external-provider responsibilities.
